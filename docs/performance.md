# 로딩·저장·커버 표시 점검

2026-09-28 코드와 로컬 브라우저에서 확인한 내용입니다. 운영 서버의 응답 시간이나 실제 아이폰의 네트워크 속도를 측정한 결과는 아닙니다.

| 구간 | 확인한 지연 원인 | 변경 |
| --- | --- | --- |
| 저장 API | DB 저장 뒤 수신자별 푸시 전송까지 기다린 후 응답 | 저장된 데이터를 응답하고 알림은 Vercel `waitUntil`로 처리 |
| 저장 화면 | 성공 콜백이 전체 곡·평가·회원·토론의 재조회까지 대기 | 서버에서 확인한 곡·평가·답글로 해당 캐시만 갱신. 진행 중이던 옛 조회는 취소 |
| 최초 목록 | 페이지 수를 몰라 마지막에 빈 페이지를 추가 조회 | 첫 응답의 정확한 총개수로 종료. 서버의 페이지 상한이 작아도 누락 없이 조회 |
| 초기 설정 | 새로 열 때마다 공개 설정 API를 캐시 없이 요청 | 정상 공개 설정만 브라우저/CDN에서 5분 캐시. 누락된 설정과 푸시 키 응답은 캐시하지 않음 |
| 실시간 갱신 | 답글 하나가 바뀌어도 전체 라이브러리와 주제를 재조회 | 변경된 테이블에 따라 필요한 쿼리만 무효화 |
| 커버 이미지 | 52px 목록 썸네일도 600px 요청 | Apple CDN에만 `srcset` 적용. 표시 크기와 기기 해상도에 따라 64~960px 선택. 첫 커버 우선 로딩, 나머지 지연 로딩 |
| 일시적 연결 오류 | 백그라운드 조회 실패도 앱 전체 오류 화면으로 전환 | 이미 받은 데이터와 작성 중인 폼을 유지 |
| 오류 재시도 | Supabase SDK의 재시도와 React Query의 재시도가 중복 적용 | 목록·토론은 React Query에서만 재시도. 저장 후 확인 조회 실패는 추가 재시도 없이 기존 방식으로 복구 |

저장 결과를 다시 읽지 못하거나 이전 버전 API에서 새 응답 필드를 받지 못하면 기존 재조회 방식으로 복구합니다. 실제 DB 저장 전에는 성공으로 표시하지 않습니다. 알림은 기존 권한·중복 방지 규칙을 유지하며, [Vercel 공식 `waitUntil`](https://vercel.com/docs/functions/functions-api-reference/vercel-functions-package#waituntil)의 실행 시간 제한을 따릅니다. DB 마이그레이션은 필요하지 않습니다.

검증은 전체 목록 재조회를 막은 상태에서 평가·답글이 표시되는지, 이전 조회가 저장 결과를 덮어쓰지 않는지, 알림 전송이 아직 끝나지 않았어도 저장 응답이 반환되는지를 포함합니다. 페이지당 2개를 반환하는 모의 데이터에서는 최초 테이블 요청이 기존 10회에서 6회로 줄었습니다. 2배 해상도 브라우저에서 52px 커버는 128~192px 이미지를 선택하며, 큰 홈 커버는 더 큰 이미지를 선택하는지 검사합니다. 이는 요청 수와 동작 검증이며 운영 환경의 시간 단축률은 아닙니다.

전체 곡과 평가 요약을 처음에 모두 받는 구조는 남아 있습니다. 데이터가 크게 늘면 활성 목록·방출 목록·집계를 서버에서 나누고 페이지별로 읽는 것이 다음 개선 지점입니다. 그 전에는 운영 네트워크 기록으로 `/api/config`, Supabase 조회, `/api/save-activity`, 이미지 CDN의 대기 시간과 전송량을 따로 확인하고, Vercel 함수와 DB의 실제 배포 지역도 확인해야 합니다.
